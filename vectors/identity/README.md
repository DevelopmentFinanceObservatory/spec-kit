# vectors/identity

Language-neutral conformance fixtures: canonical-bytes and `spec_id` vectors for the identity scheme (projection, JCS canonicalisation, SHA-256 minting). This suite is the normative artifact: a divergence between an implementation and these vectors resolves against the vectors, none waived. Each file is one vector record validated against `schemas/vectors/identity-vector.schema.json`; see `schemas/vectors/README.md` for the record format, the positive/negative split, the failure-category vocabulary, the file-layout rationale, and the full coverage plan mapping every requirement to a named vector.

The flow examples use `origin` and `destination` entity roles, alongside
`observationAbout` where the observed subject is needed. Entity role keys remain
generic: the identity core validates and canonicalises the declared keys rather
than imposing a closed role vocabulary.

A unit facet's `request.currency` member is a different case: it is either an upper-case ISO 4217 string, or a role object, `{"role": "observationAbout" | "origin" | "destination"}`, drawn from a _closed_ three-key vocabulary. The unit currency role set is fixed, in contrast to the open `entities` role keys above which any spec may declare. Whether the named role is one the spec's shape actually declares is a consumer's check against the shape, not this scheme's; the `unit-request-currency-role-*` vectors exercise only the shape of the role object itself.

111 vectors are drafted (48 positive, 63 negative), covering every planned behaviour except one. Every limit number is published in the implementation itself, so the structural- and schema-limit vectors are drafted like any other, not deferred. The one row still deferred, `limit-schema-facet-axes-over-limit`, is inexpressible while the axis vocabulary stays closed at three axes: there is no fourth legal axis name to build an over-limit case with (see `schemas/vectors/README.md`'s coverage plan, which names every vector, drafted and deferred alike, and explains this case in full).

Four vectors deliberately share one `spec_id`, `spec_7387b98bcc3394572e11ccd3d8266112`: `facets-explicit-empty-object-converges`, `facets-omitted-member-converges`, `entities-single-member-stays-array`, and `slot-singleton-set-collapse` all normalise to the suite's one common minimal fixture (a single bound slot, one entity role, no facets, an `all` window), each having started from a different equally-legal spelling of it: an explicit empty facets object versus an omitted facets member, a single-member entity array, and a singleton slot set. `tools/validate_vectors.py` does not require `spec_id` to be unique across the suite for exactly this reason. Run `uv run tools/validate_vectors.py` after adding or editing a vector; CI runs it on every push and pull request.

`binding-states-all-unbound-retained` proves the unbound-slot-retention rule for a slots array with no bound survivor at all (two entries, both unbound), a step past `binding-states-unbound`'s mixed one-bound-one-unbound case; both entries survive in `expected_projection`. `binding-states-no-slots-declared-diverges-from-all-unbound` shares the same shape/entities/window but declares no slots at all, and mints a different `spec_id` from it: a shape carrying declared-but-unbound slots is a different identity from one declaring none, and the two vectors pin that divergence pair.

`binding-states-exact` and `binding-states-value-diverges-from-exact` pin the same kind of divergence pair for the new `exact` state: both vectors share shape, entities, and window, and bind the identical slot property to the identical ref, differing only in binding state (`exact` versus `value`). They mint two different `spec_id`s regardless of whatever hierarchy the ref's code system declares, since `exact(ref)` and `value(ref)` are distinct identities by construction, not only where they happen to denote different sets of codes; `docs/identity-v1.md` states that denotation rule, which no vector can pin on its own.

`facet-null-ref-measurement-method` and `facet-null-ref-unit` pin a facet `value` binding whose `ref` is `null`: the ask for facets that declare no value on that axis. The first shares everything but that binding with the common minimal fixture and mints a different id, so a null ref is never read as an unbound axis. `facet-null-ref-provenance-rejected`, `facet-set-null-member-rejected` and `slot-null-ref-rejected` pin where a null ref refuses; `docs/identity-v1.md` states the denotation.
