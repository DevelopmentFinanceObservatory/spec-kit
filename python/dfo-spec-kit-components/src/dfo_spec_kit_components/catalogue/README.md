# python/dfo-spec-kit-components/src/dfo_spec_kit_components/catalogue

This is the presentation contract bundle: the envelope and component JSON Schemas that resolved payloads validate against, the write-side intent grammar that client requests validate against before they reach the assembler, worked and minimal intents, resolved-payload fixtures, constraint fixtures, and the manifest that digests all of it.

## Package data

The bundle ships as package data inside `dfo_spec_kit_components` (`src/dfo_spec_kit_components/catalogue/`, installed at `dfo_spec_kit_components/catalogue/`), the same layout `dfo_frame_grammar` uses for its golden vector suite. Installing the package delivers the schemas, the grammar, and the fixtures, and installs `dfo-spec-kit-descriptions`, whose `description.schema.json` and `steps.schema.json` a validator registers by `$id` beside the component schemas. `dfo_spec_kit_components.bundle_dir()` locates the installed bundle from a repo checkout and from a wheel.

## Format

| Path                                             | Contents                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `manifest.json`                                  | `catalog_version`, `schema_version`, a `sha256:`-prefixed digest of every other JSON artifact in this bundle, `referenced_schemas` (the same digest, by `$id`, of each schema outside the bundle that the envelope validates through: `description.schema.json` and `steps.schema.json` in `dfo-spec-kit-descriptions`), `encoding_classes` and `retry_modes` per component/code, and the `formatter_profile` resolved payloads are formatted against.                                                                                                                                                                                                                                                                                                                                                                                  |
| `schemas/intent.v0.json`                         | The write-side intent grammar, a draft 2020-12 `oneOf` over the six writable component shapes (`line_chart`, `bar_chart`, `table`, `stat_card`, `note_narration`, `source_card`). It validates a create or revise intent before the assembler sees it. The assembler's named rules (the one-arrayed-dimension rule, data-judged bindings) apply on top, because JSON Schema cannot express rules over open dimension keys. This release ships all six writable types. An intent naming a type a narrower release does not serve refuses with the `release_mismatch` code.                                                                                                                                                                                                                                                               |
| `schemas/envelope.schema.json`                   | The one shape every resolved component payload has: `schema_version`, `catalog_version`, `component_id`, `revision`, `provenance`, an optional `description`, and a `component` closed to the members this release ships. `description` is the card revision's description, a `$ref` by `$id` to `description.schema.json` in `dfo-spec-kit-descriptions`. A payload with one holds lineage alone in `provenance` (`inputs`, `execution_ref`, `generated_at`, `refreshed_from`), and its `source_ref` values name `description.sources[].ref`. A data card issued without one keeps `sources`, `freshness`, `warnings` and `citation` in `provenance`, and its `source_ref` values name `provenance.sources[].id`, held to the `src_` pattern; a narration note, which draws no data, carries lineage alone.                            |
| `schemas/component/*.schema.json`                | One resolved-payload schema per catalogue member (`line_chart`, `bar_chart`, `table`, `stat_card`, `note_narration`, `source_card`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `intents/*.minimal.json`                         | The smallest intent that validates against `schemas/intent.v0.json` for each member: one dimension, one value, nothing else where the member's shape has a `select`; `note_narration`'s is `{type, text}` and `source_card`'s is `{type, frame_ref}`, the member's whole writable shape.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `fixtures/<member>/intent.json` + `payload.json` | A worked example per member: an intent that validates against the grammar, paired with the resolved envelope-and-component payload that intent produces. `fixtures/bar_chart/payload_span.json` adds an entity-mode bar whose bars cover the span `2018/2022`. `fixtures/stat_card/payload_composed_unit.json` and `fixtures/table/payload_composed_unit.json` carry a composed unit. `fixtures/line_chart/payload_description.json` carries a card-revision description, and `fixtures/note_narration/payload_lineage.json` a lineage-only provenance. `fixtures/line_chart/intent_relative_window.json` and `fixtures/stat_card/intent_relative_change.json` are intents that state their periods relative to the latest one; they have no paired payload, because a payload carries the period labels a relative period resolved to. |
| `fixtures/constraints/<constraint_id>/*.json`    | Positive and negative cases for the assembler's five named constraints (`comparable_units_required`, `log_scale_requires_positive_values`, `range_contains_visible_data`, `stat_change_basis_observed`, `bar_zero_in_domain`). Each constraint reasons across several fields or against frame data, beyond what a JSON Schema can judge. `comparable_units_required` carries a composed pair: two series with equal composed units pass, and two whose denominators differ refuse.                                                                                                                                                                                                                                                                                                                                                      |

## The selector shape

An intent's `select` is a flat object mapping dimension name to value. A value is a single string or, for at most one dimension, an array of strings. A one-value binding is a plain string, `{"stat_var": "health_oda"}`. The shape comes from the grammar itself (`schemas/intent.v0.json`). The assembler judges completeness of the selection, the one-arrayed-dimension rule, and whether a named value exists in the referenced frame.

## Relative periods

Each of `window.start`, `window.end`, and the `change.basis` periods of a `stat_card` is a period label or a relative period, `{"anchor": "latest", "offset": n}` with an integer `n` of 0 or less (`$defs.relative_period` in `schemas/intent.v0.json`). `latest` is the newest period that at least half of the component's series hold, and `offset` counts back from it in whole periods at the frame's grain. The stored intent keeps the relative form, so each draw resolves it again on the frame it draws from, and the resolved payload carries period labels only. `dfo_frame_grammar.rolling` (`latest_anchor`, `shift_period`) is the one implementation of the rule.

## The unit slot

`stat_card`, each `line_chart` and `bar_chart` series, and each `table` row carry a `unit`. It takes one of four forms, and Presentation passes each through without converting it.

| Form       | Shape                                                             | Example                                                                                                     |
| ---------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| No unit    | `null`                                                            | `null`                                                                                                      |
| String     | 1 to 200 characters: the unit's graph name, or its ref            | `"US Dollar"`                                                                                               |
| Structured | `structured_unit`: `currency`, `magnitude`, `prices`, `base_year` | `{"currency": "USD", "prices": "constant", "base_year": 2023}`                                              |
| Composed   | `composed_unit`: `numerator` and `denominator`, both required     | `{"numerator": "US Dollar", "denominator": {"stat_var": "dcid:Count_Person", "label": "Total population"}}` |

A composed unit is the unit of a quotient of two measures and reads `<numerator> per <denominator>`. Each part is a string, a `structured_unit`, or a `counted_stat_var`. A part is never `null` and never itself a composed unit.

A `counted_stat_var` stands for a measure that declares no unit, such as a population count. It names the StatVar in `stat_var`, a `dcid:`-prefixed reference, and carries the text a renderer prints in `label`, which is the StatVar's graph name or the reference without `dcid:` when the graph has none.

The four unit-bearing schemas each hold their own copy of `structured_unit`, `composed_unit`, `unit_part` and `counted_stat_var` under `$defs`. `tests/test_shared_defs_consistency.py` keeps the copies identical.

## Adding a schema or fixture

1. A schema change starts in the normative presentation contract this bundle implements.
1. Add or edit the JSON file under `schemas/`, `intents/`, or `fixtures/`.
1. Regenerate `manifest.json`'s digest for every artifact you touched, and add an entry for a new file. Each digest is `"sha256:" + hex(sha256(file_bytes))`, computed over the file exactly as it sits on disk.
1. Confirm every intent under `intents/` and `fixtures/*/intent.json` validates against `schemas/intent.v0.json`, every payload under `fixtures/*/payload.json` validates against `schemas/envelope.schema.json`, and `uv run pytest` passes from `python/dfo-spec-kit-components/`.
