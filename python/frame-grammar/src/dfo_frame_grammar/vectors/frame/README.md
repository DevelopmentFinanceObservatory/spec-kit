# python/frame-grammar/src/dfo_frame_grammar/vectors/frame

This is the frame grammar's golden vector suite: the language-neutral conformance target for `docs/frame-grammar-v1.md`. Where that document and these vectors disagree, **the vectors win**, and the disagreement is a release blocker. `frame-vector.schema.json` (draft 2020-12, `$id` `https://raw.githubusercontent.com/DevelopmentFinanceObservatory/spec-kit/main/python/frame-grammar/src/dfo_frame_grammar/vectors/frame/frame-vector.schema.json`) validates every vector file in this directory. This document defines the frozen record format and the `format_version`.

Every vector's expected output here is captured from this repository's own implementation (see "Adding a vector" below), not from an independent second implementation. This suite proves this implementation's own output has not drifted from a previously recorded value — a regression pin — not that `docs/frame-grammar-v1.md` is independently reproducible by a second implementation that has never read this code. That independent conformance evidence still needs a second implementation, in a different language, to be built and checked against this same suite.

## Package data, not a repo-level vector directory

This kit's other conformance suite, the identity vectors, lives at repo-level `vectors/identity/`, with its record schema at `schemas/vectors/`, outside any installed Python distribution (see `vectors/identity/README.md`). This suite deliberately does not follow that layout: it ships as package data inside `dfo_frame_grammar` itself (`src/dfo_frame_grammar/vectors/frame/*.json`, installed at `dfo_frame_grammar/vectors/frame/*.json`), and `frame-vector.schema.json` ships the same way, alongside the vectors it validates.

The reason is what an installed distribution carries and what it does not. A repo-level vector directory is not part of any wheel or sdist; a consumer that installs this package rather than cloning this repository has no path to it at all unless it also checks out a copy of this repository and points an environment variable at it. That is exactly the shape of gap this suite is built to close: two independent consumers — a REST API and an in-process library embed — are contractually required to reproduce the identical canonical bytes and tokens from the identical vector suite, and a suite that only exists behind an optional checkout can silently run against zero vectors in exactly the environment (an installed package, no sibling checkout beside it) where a consumer is most likely to be running it. Shipping the vectors and their schema as package data means an installed `dfo_frame_grammar` always carries its own conformance suite; there is no environment gate to forget and no checkout step that can be skipped.

`tools/validate_frame_vectors.py` (repo root) checks every vector's well-formedness and internal byte/token consistency **without importing `dfo_frame_grammar`** -- see "Two validators, two jobs" below. `python/frame-grammar/tests/test_vectors.py` drives the real implementation against every vector. CI runs both on every push and pull request.

## Format

Each vector is one JSON file, one record. There is no wrapping array file: one file per vector, named `<name>.json` where `<name>` matches the record's own `name` field, so adding a vector is exactly "add one file" with no second file to keep in sync. Every record carries:

| Field              | Meaning                                                                                                                                                                                                                                                                                                        |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `format_version`   | The vector record format's own version, pinned to `2`. Independent of `docs/frame-grammar-v1.md`'s own document version (`FRAME_GRAMMAR_VERSION`) and of `frame_version`/`identity_version` (`"frame1"`/`"cv2"`), the byte-rule domain separators -- four separate version axes kept deliberately independent. |
| `name`             | The vector's stable, unique, kebab-case id. Matches the filename stem.                                                                                                                                                                                                                                         |
| `description`      | One-line statement of what the vector proves.                                                                                                                                                                                                                                                                  |
| `kind`             | `"frame"` or `"content_version"`. See the two record shapes below.                                                                                                                                                                                                                                             |
| `classification`   | `positive` or `negative`. See "The positive/negative split" below.                                                                                                                                                                                                                                             |
| `coverage`         | Dot-separated tags naming what the vector exercises. Free to grow, not a frozen vocabulary.                                                                                                                                                                                                                    |
| `notes`            | Optional free-form context.                                                                                                                                                                                                                                                                                    |
| `failure_category` | Negative only. See "Failure-category vocabulary" below.                                                                                                                                                                                                                                                        |

### `kind: "frame"`

Proves one frame's canonical bytes and the `content_version` minted over it end to end.

| Field                      | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `role_keys`                | The shape's declared entity role property references, in whatever order they were declared (column order is a derived property, not an input -- see `expected_columns`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `rows`                     | The frame's input rows: a JSON array of objects, each keyed by column name (`stat_var`, one key per `role_keys` entry, `time_period`, `value`, and optionally `unit`/`measurementMethod`/`provenance`). A `unit` value is `null`, a unit ref string, a unit-request object (`{currency, prices, base_year, recipe}`, `recipe` optional), or a composed-unit object `{"numerator": <part>, "denominator": <part>}` whose parts are a unit ref string, a unit-request object, or `{"stat_var": "dcid:..."}`. This is the frame's pre-canonicalisation input, in whatever order the vector author chose to type it in -- input row order carries no meaning, and some vectors deliberately pair an input order with a shuffled order to prove that (see "Convergence pairs" below). |
| `expected_columns`         | Positive only. The exact `columns` array a conformant implementation must derive from `role_keys`: `stat_var`, the role columns (NFC code point order), `time_period`, `value`, `unit`, the facet-identity columns, `status` last.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `canonical_bytes`          | Positive only. The exact JCS bytes of `expected_document`, lossless hex-encoded.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `expected_document`        | Positive only. The fully normalised closed frame document (`{"frame_version": "frame1", "columns": [...], "rows": [...]}`) `canonical_bytes` must be the JCS serialisation of -- built from `rows` above after every construction-time rule this grammar pins: NFC normalisation, int/float value convergence, row sorting, and the reserved `status` column populated `null`. This is what breaks the circularity a bytes-only vector would have: a reader, or `tools/validate_frame_vectors.py`, can check `canonical_bytes == JCS(expected_document)` by eye or by running JCS directly, without ever calling into this implementation. It also makes column order and row order visible and reviewable in the vector file itself.                                            |
| `expected_frame_sha256`    | Positive only. The full 64 lowercase hex SHA-256 digest of the bytes decoded from `canonical_bytes`. Included as an independently checkable intermediate value, since it is also the `frame_sha256` member of the `content_version` preimage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `expected_preimage`        | Positive only. The closed `content_version` preimage document (`{"identity_version": "cv2", "frame_sha256": ...}`) minting must build from `expected_frame_sha256`. `expected_content_version` must be exactly `"cv_"` plus the first 32 lowercase hex characters of SHA-256(JCS(`expected_preimage`)) -- checkable independently of the implementation, the same way `expected_document` breaks the circularity one level down.                                                                                                                                                                                                                                                                                                                                                 |
| `expected_content_version` | Positive only. The full public `cv_`-prefixed token that minting `expected_frame_sha256` must produce.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

A conformance run against a `"frame"` vector does three checks: build a frame from `role_keys`/`rows` and diff its columns against `expected_columns`; canonicalise it and compare the resulting bytes, byte for byte, against `canonical_bytes`; and mint a `content_version` from the resulting digest, checked against `expected_content_version`. A negative `"frame"` vector carries only `role_keys`/`rows` and `failure_category`: the input is refused during frame construction itself, before any `content_version` preimage is ever built.

### `kind: "content_version"`

Proves the `cv2` preimage and public token independent of any specific frame -- used for a digest-level refusal a full frame build would never reach (a malformed `frame_sha256`), so the vector does not need a whole, otherwise-valid frame just to exercise it.

| Field                      | Meaning                                                                                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `frame_sha256`             | The `frame_sha256` supplied directly as the minting input, standing in for a real frame's digest. A positive vector carries 64 lowercase hex characters; a negative vector carries the malformed digest minting refuses. |
| `expected_preimage`        | Positive only. Same shape as the `"frame"` kind's field above, built from `frame_sha256`.                                                                                                                                |
| `expected_content_version` | Positive only. Same meaning as the `"frame"` kind's field above.                                                                                                                                                         |

A negative `"content_version"` vector carries `frame_sha256` plus `failure_category`; minting must refuse before ever producing a preimage or token.

## The positive/negative split

A **positive** vector's input builds cleanly and, where the kind mints a token, mints one: it carries every `expected_*` field its `kind` and step reach, and never `failure_category`. A **negative** vector's input is refused: it carries `failure_category` and none of the `expected_*` fields. `frame-vector.schema.json` enforces this with `if`/`then` keyed on `kind` and `classification`, so a vector cannot accidentally carry both an expected output and a failure category, or neither.

## Failure-category vocabulary

Categories are lower_snake_case, few, and permanent once published: a changed meaning gets a new category, never a redefinition under the same spelling. Every category below is drawn directly from `dfo_frame_grammar.grammar.FrameError.category` and `dfo_frame_grammar.content_version.ContentVersionError.category`, whose own docstrings are this vocabulary's authoritative definition; the summaries here restate them for a reader of this suite. `unknown_member`, `invalid_facet_axis`, `invalid_facet_basis`, `invalid_facet_ref`, `duplicate_source`, `duplicate_axis`, and `conversion_null` are retired with the `cv1` preimage that raised them and are never reused.

| Category              | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema_violation`    | A malformed input this package has no more specific name for: an unknown or missing row column, a cell of the wrong type, a role key colliding with a reserved column name, a `stat_var` not spelled with the `dcid:` prefix, or an empty-string ref cell.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `lone_surrogate`      | A string contains an unpaired UTF-16 surrogate code point.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `non_finite_number`   | A `value` cell is `NaN` or `±Infinity` rather than a finite double, or an integer too large to convert to a finite double at all.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `invalid_time_period` | A `time_period` string is not `YYYY`, `YYYY-MM`, or `YYYY-MM-DD`, zero-padded, with ASCII digits only, or an interval `<start>/<end>` of two such points at one grain with `start` before `end`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `invalid_unit`        | A unit-request object (frame `unit` cell) violates its closed shape: an unknown member, a missing `currency`/`prices`, a `currency` that is not upper-case ISO 4217, a non-string or invalid `prices` value, `base_year` present/absent inconsistently with `prices`, a `base_year` outside the JCS-serialisable integer domain (magnitude greater than 2\*\*53 − 1), or a `recipe` that is not a non-empty string, as checked by `grammar.validate_unit_request`. A composed-unit object violates its closed shape: a member beside `numerator` and `denominator`, either one missing, or a part that is `null`, an empty string, itself a composed unit, an invalid unit-request object, or a `stat_var` object with another member or a `stat_var` that is not a `dcid:`-prefixed string. |
| `duplicate_row_key`   | Two rows share the same grain (every cell except `value` and `status`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `invalid_digest`      | `frame_sha256` is not exactly 64 lowercase hex characters.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## Two validators, two jobs

`tools/validate_frame_vectors.py` and `python/frame-grammar/tests/test_vectors.py` deliberately do different, non-overlapping jobs, the same split this kit's own identity vector suite draws between `tools/validate_vectors.py` and its own pytest harness (`python/spec-kit/tests/test_identity_vectors.py`).

`tools/validate_frame_vectors.py` checks every vector file's own internal consistency: does it conform to `frame-vector.schema.json`; does its filename match its `name`; is every `name` unique; are both classifications non-empty; does the suite meet its minimum count floor; and, for every positive vector, is `canonical_bytes` genuinely `JCS(expected_document)`, is `expected_frame_sha256` genuinely `SHA-256(canonical_bytes)`, and is `expected_content_version` genuinely `"cv_"` plus the truncated `SHA-256(JCS(expected_preimage))`. Across the suite, it checks that positive vectors over one frame digest share one `expected_content_version` and that two different digests never share one. It never imports `dfo_frame_grammar`, so it cannot silently validate a vector against the very implementation the vector is supposed to pin -- if this implementation and a vector's own committed fields both drifted the same wrong way, this validator would still catch a byte-level inconsistency introduced by the drift, and a second-language implementation can run an equivalent check with no Python at all.

`python/frame-grammar/tests/test_vectors.py` drives the real implementation against every vector: it builds a frame (or mints a token) from a vector's raw input and asserts the live result matches that vector's own committed expectation, and, for a negative vector, asserts the implementation refuses with the vector's own `failure_category`. This is the only one of the two that can catch this implementation itself drifting from a vector's committed expectation.

## Convergence pairs

Some vectors are deliberately authored in pairs that share an identical `expected_content_version` (and, for two `"frame"` vectors, an identical `canonical_bytes` too) despite structurally distinct input, to prove a specific convergence rule rather than merely assert it:

- `frame-row-order-input-converges` / `frame-row-order-shuffled-converges` -- the same four rows in two different input orders.
- `frame-value-int-spelling-converges` / `frame-value-float-spelling-converges` -- one observed value spelled as a Python int versus a Python float.
- `frame-unicode-decomposed-converges` / `frame-unicode-precomposed-converges` -- one facet reference spelled as decomposed versus precomposed Unicode.
- `frame-multi-role-unicode-order` / `frame-row-key-decomposed-spelling-converges` -- the same non-ASCII role, spelled precomposed versus decomposed, as both a declared role key and a row mapping key.

A vector consumer should not assume `name` uniqueness implies `expected_content_version` (or `canonical_bytes`) uniqueness across the suite: these deliberate pairs collide by design, not by accident.

## Adding a vector

1. Confirm the behaviour is defined in `docs/frame-grammar-v1.md`. This suite makes decided grammar rules executable; it does not decide them.
1. Pick a `name` not already used, and a `kind` matching what the vector needs to exercise (see the two record shapes above).
1. For a positive vector, compute every expected field mechanically, from the real implementation (`dfo_frame_grammar.frame.Frame.build`, `canonical_frame_bytes`, `dfo_frame_grammar.content_version.mint_content_version`, plus the JCS/SHA-256 relationships `expected_document`/`expected_preimage` themselves encode), never by hand. For a negative vector, confirm live which `failure_category` the real implementation raises for the chosen input, and use exactly that spelling from the frozen vocabulary above.
1. Write `<name>.json` and confirm both `uv run tools/validate_frame_vectors.py` and `uv run pytest python/frame-grammar/tests/test_vectors.py` pass it.
