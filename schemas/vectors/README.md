# schemas/vectors

The identity vector suite is the language-neutral conformance target for the identity projection and canonicalisation algorithm (`dfo_spec_kit.identity.core`). It is a set of fixtures that any implementation, in any language, must reproduce byte-for-byte and refusal-for-refusal. `schemas/vectors/identity-vector.schema.json` (draft 2020-12, `$id` `https://raw.githubusercontent.com/DevelopmentFinanceObservatory/spec-kit/main/schemas/vectors/identity-vector.schema.json`) validates every file under `vectors/identity/`. The `$id` sits under the repo's own raw-content path for the same reason as the code registry's. The kit has no schema-hosting service yet, and a schema `$id` should stay stable once published, so it only moves the day a real hosting location exists. This document defines the frozen record format and the format_version. `vectors/identity/` carries the authored suite against a floor of at least 25 positive and negative vectors. `tools/validate_vectors.py` (see `tools/README.md`) checks every vector's well-formedness and internal byte/id consistency, and CI runs it on every push and pull request.

## Format

Each vector is one JSON file, one record, validated independently against `identity-vector.schema.json`. There is no wrapping array file (contrast `registries/codes.json`, one file holding every registry entry). See "File layout" below for why.

```json
{
  "format_version": 1,
  "name": "entities-array-sort-dedup",
  "description": "An entity role's array is sorted and de-duplicated by NFC code point order before hashing.",
  "identity_version": "spec1",
  "classification": "positive",
  "coverage": ["entities.sort-dedup"],
  "input": { "...": "..." },
  "expected_projection": { "...": "..." },
  "canonical_bytes": "7b22656e74697469...",
  "spec_id": "spec_02fa583541051eff4463a37159593bd0"
}
```

Fields:

| Field                   | Meaning                                                                                                                                                                                                                                       |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `format_version`        | The vector record format's own version. Pinned by the schema (`1` today), independent of `identity_version` and the canonical definition's `schema_version` -- three separate version axes, kept deliberately independent.                    |
| `name`                  | The vector's stable, unique, kebab-case id. Matches the filename stem, so renaming the file is the rename.                                                                                                                                    |
| `description`           | One-line statement of what the vector proves.                                                                                                                                                                                                 |
| `identity_version`      | The identity_version this vector targets. Currently pinned to `"spec1"`; a future identity_version gets its own vector set validated by its own schema version, never mixed into this one, since identity_version rotates the hash by design. |
| `classification`        | `positive` or `negative`. See below.                                                                                                                                                                                                          |
| `coverage`              | Dot-separated tags (e.g. `window.range.half-open-start`) naming what the vector exercises, used to check suite coverage against the coverage plan below. Free to grow, not a frozen vocabulary like `failure_category`.                       |
| `notes`                 | Optional free-form context: a pointer to the specific rule the vector enforces, or a caveat for whoever reads the fixture next.                                                                                                               |
| `input` / `input_bytes` | The input, in one of two mutually exclusive forms. See "input vs input_bytes" below.                                                                                                                                                          |
| `expected_projection`   | Positive only. The fully normalised identity-core projection (the identity projection shape) the input must build, before JCS serialisation.                                                                                                  |
| `canonical_bytes`       | Positive only. The exact JCS (RFC 8785) output for `expected_projection`, lossless hex-encoded.                                                                                                                                               |
| `spec_id`               | Positive only. `"spec_"` plus the first 32 lowercase hex characters of SHA-256(`canonical_bytes`).                                                                                                                                            |
| `failure_category`      | Negative only. The stable category the input is refused under. See the vocabulary below.                                                                                                                                                      |

`expected_projection` is compared by structural JSON equality. Two JSON values with the same members and the same nested values are equal regardless of the order those members happen to appear in in the fixture file. Key order in `expected_projection` is not meaningful and is never asserted. JCS's key ordering is a property of the serialisation stage, not of the pre-serialisation projection a conformance run compares `expected_projection` against. Byte-for-byte comparison only enters at `canonical_bytes`, an exact hex string. A conformance run against a vector therefore does two separate checks, never one: structural equality between the built projection and `expected_projection`, and byte equality between the JCS output and `canonical_bytes`.

An explicit empty facets object and an omitted facets member express the same intent, no axis bound, and mint the same id. `facets-explicit-empty-object-converges` and `facets-omitted-member-converges` are otherwise identical vectors that deliberately share one `spec_id`, proving the convergence rather than colliding by accident. A second deliberate pair, `numeric-integer-spelling-converges` and `numeric-float-spelling-converges`, shares a different `spec_id` the same way: an integer literal and a float literal that evaluate to the identical IEEE-754 double mint the identical id regardless of how the source spelled it. Two open-roles pairs share ids the same way: `open-roles-empty-list-converges` mints the id of `open-roles-absent-origin-diverges`, which omits the member, and `open-roles-unsorted-duplicated-converges` mints the id of `open-roles-sorted`. `tools/validate_vectors.py` does not require `spec_id` to be unique across the suite for this reason. Only `name` is required unique. Two further vectors land on the facets pair's id incidentally, since all four use the suite's common minimal fixture (a single bound slot, one entity role, no facets, an `all` window) as their resting state: `entities-single-member-stays-array` and `slot-singleton-set-collapse` reach it from a single-member entity array and a singleton slot set respectively. All four normalise to the identical projection.

The suite states convergence with a shared `spec_id`; it states its converse, divergence, with a pinned pair of distinct ids instead. `binding-states-all-unbound-retained` and `binding-states-no-slots-declared-diverges-from-all-unbound` share the same shape, entities, and window but differ on slots (two declared-but-unbound entries versus none at all) and mint two different ids, pinning that a shape carrying unbound slots mints a different identity from a shape declaring none. `open-roles-open-origin` and `open-roles-absent-origin-diverges` differ only in `open_roles: ["origin"]` and mint two different ids, pinning that an open role is a different ask from an absent one.

No year floor exists in this schema version, so `-0` is valid input. `numeric-negative-zero` is drafted as a positive vector proving the canonical serialisation collapses negative zero to `0`, verified against the reference JCS implementation (`rfc8785.dumps({"x": -0.0})` produces `{"x":0}`). The vector is not a claim that year `0` is a meaningful calendar year. Its `notes` field says so explicitly, so a reader is not left assuming the suite treats that as domain-legal on any other grounds.

## The positive/negative split

A **positive** vector's input canonicalises and mints an id: it carries `expected_projection`, `canonical_bytes`, and `spec_id`, and never `failure_category`. A **negative** vector's input is refused before minting: it carries `failure_category` and never the three positive-only fields. The schema enforces this with `if`/`then` keyed on `classification`, so a vector cannot accidentally carry both an expected id and a failure category, or neither. This mirrors the identity core's own closed, no-partial-result design: refuse rather than silently drop a partial result. A vector is either a clean success or a clean refusal, never a hybrid.

## input vs input_bytes

A vector carries exactly one of `input` (a parsed JSON value, embedded directly in the record) or `input_bytes` (the exact input document's UTF-8 bytes, lossless hex-encoded). Use `input` whenever the vector's outcome does not depend on the precise bytes the strict parser sees. Testing sort order, de-duplication, singleton collapse, sparse omission, and most binding-shape checks needs nothing more than valid parsed JSON, and embedding it directly keeps the fixture readable and diffable.

Use `input_bytes`, and only `input_bytes`, whenever the outcome (success or failure) depends on input encoding: duplicate object keys (a re-serialised `input` field would silently lose the duplicate the moment any tool round-trips the vector file through a standard JSON parser), lone surrogates, `NaN`/`Infinity` literals, numbers outside I-JSON's representable range, decomposed versus composed Unicode, or escaped-JSON forms (`\uXXXX` sequences that must decode to the same code point as a literal UTF-8 byte sequence). Most of these cases are technically parseable as `input`, but a vector file is itself JSON, and re-serialising it through a consuming tool's own JSON writer could accidentally normalise away the exact byte-level distinction under test. `input_bytes` sidesteps that. It is opaque hex, decoded once, fed straight to the strict parser under test, with no intermediate tool getting a chance to launder it.

The choice also marks where in the identity algorithm a vector starts exercising the implementation under test. An `input_bytes` vector begins at the strict parse stage itself, so it can prove how a conformant parser handles raw text that a lenient decoder might silently normalise or accept. An `input` vector is already parsed JSON. It says nothing about strict-parse behaviour, and begins exercising the implementation from the schema-validation stage onward. A structural-limit vector (max definition bytes, nesting depth, string length, number length) uses `input_bytes` even when its outcome does not depend on encoding, because the limit itself is enforced at the strict parse stage, and the vector must begin there to prove the byte parser enforces it, not merely that already-parsed JSON at the boundary passes schema validation.

`input_bytes` composes with either classification. A **positive** byte-level vector is fully expressible. Decomposed Unicode input that successfully normalises to NFC is `input_bytes` plus `expected_projection`/`canonical_bytes`/`spec_id`, like any other positive vector (see `vectors/identity/unicode-decomposed-nfc.json`). Encoding sensitivity and success/failure are orthogonal; the schema does not couple them.

Encoding choice for both `input_bytes` and `canonical_bytes`: **lowercase hex**, not base64. The bytes are UTF-8 JSON text, almost entirely printable ASCII with occasional multi-byte sequences for the Unicode vectors; hex keeps every byte visible as two characters with no alphabet edge cases (no padding, no URL-safe/standard variant to pick), makes a single-byte diff land on an even character boundary in a code review, and matches the lowercase-hex convention `spec_id` itself already uses, so the suite has one byte-encoding convention throughout rather than two.

## Failure-category vocabulary

Categories are lower_snake_case, few, and permanent once published. The addition rule mirrors `registries/codes.json`'s (schemas/registry/README.md): a changed meaning gets a new category, never a redefinition under the same spelling. This vocabulary is deliberately separate from `registries/codes.json`. That registry names permanent codes across the Search API's transports (problem-details bodies, `no_data` reasons, `unsupported` reasons); this vocabulary names failure modes at the identity/projection layer itself, one level below any API surface, before a consumer maps a category into its own refusal grammar (for example, `input_limit_exceeded` maps into the Search API's own refusal grammar as `request_invalid`). No two vocabularies share a spelling today.

This vocabulary names `schema_violation` once, in its binding-discriminator precedence rule: the specific `invalid_binding_shape` category wins whenever both readings apply. Everywhere else it is this suite's own catch-all for ordinary schema conformance failures not covered by a more specific category, and anchors the discriminator rule against the shape-specific categories below.

| Category                       | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `malformed_json`               | The input bytes do not parse as JSON text at all: rejected at the strict parse stage, before schema validation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `duplicate_keys`               | An object in the input repeats a key, whether the repeat is byte-identical or two byte-distinct keys that NFC-normalise to the same string: after normalisation the object repeats a key either way. The byte-identical case is rejected by the strict (I-JSON) parse layer; the NFC-colliding case is caught one stage later, once normalisation runs. Both share this category, since both are the same defect: an object that resolves to a repeated key.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `lone_surrogate`               | A string contains an unpaired UTF-16 surrogate code point, rejected at the strict parse stage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `non_finite_number`            | A `NaN` or `Infinity` token appears where a JSON number is expected, rejected at the strict parse stage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `number_out_of_range`          | A number literal is syntactically valid JSON but its finite magnitude exceeds 2^53-1, I-JSON's safely representable integer bound, rejected at the strict parse stage. | `input_limit_exceeded`         | Any structural limit (max definition bytes, nesting depth, string length, number length) or schema limit (max slots, roles, values per role, facet axes, set members) is exceeded. Both limit kinds share one category: exceeding any limit, structural or schema, is one stable parse-failure category, not one per limit type.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `schema_violation`             | A canonical-definition-schema conformance failure not covered by a more specific category below: a required member absent (including `identity_version` itself, when the member is omitted entirely rather than present with an unrecognised value), a member holding the wrong JSON type, or a violated cross-member constraint (a required-if or at-least-one-of shape, such as a `range` window carrying neither endpoint). This is the discriminator against `invalid_binding_shape` and `invalid_unit_request` below. `schema_violation` owns an absent or wrongly-typed member and the schema's own combinator constraints. Those two own a member that is present and correctly typed but combined with the wrong sibling keys for its declared `state` or request shape; when one binding presents both defects at once, the wrong-sibling reading governs and the specific category wins. A pragmatic catch-all so the suite has somewhere to put ordinary JSON Schema validation failures not enumerated as their own category, enforced at the schema-validation stage. |
| `unknown_member`               | An object carries a member its schema does not declare (`additionalProperties: false` violation), at any nesting level, rejected at the schema-validation stage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `invalid_binding_shape`        | A slot or facet binding's payload does not match its declared `state` (e.g. a `value` state carrying `refs`, or a `ref` and a `request` both present), or a facet set containing a `request` member: conversion requests may only appear in `value` form, since a set of conversion requests has no use case and is refused. A `national_currency` member follows the same rules: a `value` binding on the `unit` axis carries it as the only one of `ref`, `request` and `national_currency`, and a `provenance` or `measurementMethod` binding or a facet `set` holding one is refused. Assumes every member present is correctly typed and named; a member absent or wrongly typed is `schema_violation` instead — unless the binding also carries a wrong-family sibling for its declared `state`, in which case the wrong-sibling defect governs and the refusal stays `invalid_binding_shape`.                                                                                                                                                                               |
| `unsupported_identity_version` | `identity_version` is present but names a version this parser does not implement, checked at the strict parse stage before schema validation applies. Does not cover a missing `identity_version`. An omitted required member is `schema_violation` instead. Structural limits are checked ahead of this gate: an input that is both structurally over-limit and names an unrecognised `identity_version` refuses `input_limit_exceeded`, since the version cannot be read until the input is known to be safely parseable (see `limit-check-precedes-version-gate-rejected`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `empty_collection`             | A slot's `set` binding, an entity role's array, or a facet's `set` binding is empty: empty sets and empty role lists are invalid everywhere in the identity core.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `reversed_range`               | A `requested_window` of kind `range` has both endpoints present with `start_year > end_year`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `invalid_unit_request`         | A unit facet's `request` form violates its structural constraint: `base_year` present when `prices` is not `constant` (or absent when it is), or `currency`, when spelled as a string, is not upper-case ISO 4217. Assumes every member present is correctly typed and named; a member absent or wrongly typed is `schema_violation` instead. `currency` may also be a role object whose single member `role` holds one of the spec's entity role keys, `observationAbout`, `origin` or `destination`. Whether the spec's shape declares that role is a consumer's check against the shape. An unrecognised role name or a non-string role value is `schema_violation`, as an invalid `prices` value is, and an extra member on the role object is `unknown_member`.                                                                                                                                                                                                                                                                                                               |

**On merges.** The strict-parse rejections split into five categories (`malformed_json`, `duplicate_keys`, `lone_surrogate`, `non_finite_number`, `number_out_of_range`) rather than collapsing into one, because each is a semantically distinct parser behaviour a conformant strict I-JSON implementation must detect independently, and a vector's `failure_category` should say which behaviour it is proving, not just that the parse failed. `unknown_member` stays one category regardless of which nested object the violation occurs in (top-level, a binding, a facet), since the defect (an object carries a member its schema does not declare) is identical wherever it occurs. The `coverage` tag on each such vector records the specific location. `input_limit_exceeded` stays merged across structural and schema limits. Exceeding any limit, structural or schema, is one stable parse-failure category, not one per limit type. `empty_collection` merges slot-set, entity-array, and facet-set emptiness because all three express the same defect, no intent expressed. `invalid_unit_request` merges the `base_year`/`prices` pairing rule and the currency-case rule because both are structural violations of one conditional constraint object (the unit `request` shape), not independently meaningful failure modes.

## Fixture vocabulary

This suite tests the identity algorithm, not the ontology. The worked-example refs it uses, `developmentFinanceFlow`, `country/FRA`, `country/TGO`, `country/USA`, `country/KEN`, `Malaria`, `GrantsScheme`, `OECD_DAC2A`, and `USDollar`, the shape union's own worked-example values, `DevelopmentFinance` (`population_type`), `measuredValue` (`stat_type`), `Nominal` (`measurement_qualifier`), `Count_Person` (a `measurement_denominator` ref), and `Count_Person_Female` (a pinned-arm `id`), plus `test/`-prefixed values invented to carry encoding edge cases, are the suite's fixture vocabulary. `anotherShape` and `aggregation` are invented, once-off values naming a second shape and an illegal `kind` respectively, reserved the same way. These spellings are reserved and permanent once published, the same way a code or category spelling is once it ships.

## File layout

One file per vector, named `<name>.json` where `<name>` matches the record's own `name` field exactly (kebab-case, e.g. `window-range-half-open-start.json`). Files live flat in `vectors/identity/`, discovered by globbing `vectors/identity/*.json`. No manifest or index file lists them, so adding a vector is exactly "add one file", with no second file to keep in sync and no merge conflict between two vectors added in parallel branches. This is a deliberate departure from `registries/codes.json`'s single-file-with-an-array shape. The registry's entries are a small, slow-growing, centrally-reviewed list where one sorted file is easy to eyeball for gaps. The vector suite is expected to grow by many independent additions, one PR per edge case, and per-file review, one diff per vector, reads far better than reviewing insertions into one growing array. It also means a vector's filename doubles as its stable id in `git log`, `git blame`, and any tool that wants to name "the vector that broke" without opening the file.

`tools/validate_vectors.py` globs the directory, validates each file against `identity-vector.schema.json`, checks filename-vs-`name` consistency and `name` uniqueness, and for positive vectors independently recomputes `canonical_bytes` and `spec_id` from `expected_projection` to catch a vector whose committed expectation and committed bytes have drifted apart. It does not check `expected_projection` against `input`/`input_bytes` through a reference implementation. That would mean building the identity algorithm itself, a future implementation's job, not this fixture-format validator's.

## Coverage plan

Maps every behaviour the suite must prove to named vectors. Status `drafted` means the file exists under `vectors/identity/` and `uv run tools/validate_vectors.py` passes it. Status `deferred` means the row is named but not authored yet. Every limit number is published in the implementation itself, so 128 of 129 planned rows are drafted, 54 positive and 74 negative, well over the 25-vector floor. The one remaining row, `limit-schema-facet-axes-over-limit`, stays deferred for a structural reason rather than a numeric one: see below.

The published limits the suite now tests: 65,536 definition bytes, nesting depth 5, 1,024-code-point strings, and 16-character number literals for the structural limits; 64 slots, 16 roles, 1,024 values per role, 1,024 set members, and 3 facet axes for the schema limits. Three measurement conventions the vectors encode are worth stating explicitly: nesting depth counts open containers with the root object itself at depth 1; the values-per-role and set-members counts apply before de-duplication, so a count of raw entries past the limit refuses even if fewer distinct values remain after normalisation; and number length counts every character of the literal as written, including a sign, decimal point, and exponent marker.

The published number-length limit is 16 characters of the literal as written, and `limit-number-length-at-limit`'s literal, `9007199254740991`, is simultaneously 2^53-1, the largest integer magnitude a JSON number can represent without two distinct literals colliding on one IEEE-754 double. One vector therefore pins the length boundary and the safe-integer magnitude boundary together, deliberately placed below JCS's serialisable domain rather than at an edge where the two boundaries would conflate. The pairing holds on the positive side only: a negative integer at the magnitude boundary (`-9007199254740991`) spells 17 characters with its sign, so it refuses on length before magnitude, leaving the negative-side magnitude boundary deliberately unreachable rather than the limit loosening to 17. A facet-axes over-limit case is inexpressible while the axis vocabulary stays closed at three axes: there is no fourth legal axis name to construct an over-limit case with, so inventing one would test the closed-object/unknown-member rule instead of a limit rule. A future additive axis would make the case expressible again. The facets object is also the one exception to the schema limits' otherwise-uniform count-before-member-validity ordering (see `count-limit-precedes-member-validity-rejected`): axis-name validity is checked before the axis count, so a facets object holding every legal axis plus one unknown key refuses `unknown_member`, not `input_limit_exceeded`, since the axis vocabulary is closed and an unknown axis is a closed-object defect, not a limit defect.

## Adding a vector

1. Confirm the behaviour is defined in the identity specification. This suite makes decided semantics executable. It does not decide them.
1. Pick a `name` not already used, matching an unclaimed row in the coverage plan above where one exists, or add a new row if the vector covers something the plan missed.
1. Write `vectors/identity/<name>.json` with every field the schema requires for its `classification`. For a positive vector, compute `expected_projection` by hand-applying the identity specification's normalisation and projection-building stages to `input`, then get `canonical_bytes` and `spec_id` mechanically (`uv run --with rfc8785 python -c '...'`, `rfc8785.dumps`, `hashlib.sha256`). Never hand-compute JCS bytes or a hash.
1. Validate the file against `schemas/vectors/identity-vector.schema.json` and update its row's `Status` to `drafted` in the coverage plan table above.

## Scope

The suite tests every stage of the identity algorithm it can exercise from a fixture alone: strict parsing, schema validation, normalisation, projection-building, and canonical serialisation. Four areas sit outside that boundary, for structural reasons rather than by oversight.

Alias resolution is graph-dependent and cannot be fixture-tested without a graph. Every vector's `input` and `input_bytes` is already-canonical graph refs, so the suite exercises every stage except alias resolution itself.

Role-validity refusals, `role_not_resolved`, `invalid_role_ref`, and `role_incompatible`, are graph-dependent for the same reason. `entities-observation-about-plain-subject` exercises the shape of the `observationAbout` role without touching graph-dependent validity.

The dense-slots invariant names two distinct claims, one graph-dependent and one not. That every shape-declared slot appears on the _wire_, at minimum as `unbound`, needs the shape registry's full declared-slot set to verify completely, the same graph dependency as role validity: `binding-states-unbound` proves only that one slot's `unbound` state serialises correctly in isolation, not that a shape's complete declared-slot set is present on the wire for every definition built from it. That an `unbound` slot entry is _retained in the hash projection_ is, by contrast, fully fixture-testable and is tested: `binding-states-unbound` proves the retention for a dense wire document carrying one bound and one unbound slot, and `binding-states-unbound-reprojects-to-itself` proves the retention is idempotent by starting from that same canonical form and showing it is a fixed point.

`schema_version` rejection is out of scope for a structural reason rather than a graph-dependency one. `schema_version` is not a member of the identity core; it lives one level up, in the canonical definition's wire wrapper. A vector whose `input`/`input_bytes` is the identity-core projection cannot carry a `schema_version` to reject in the first place. That rejection belongs to whatever validates the canonical-definition wire schema, not to this identity/projection-layer suite.

## Unit vectors

`vectors/units/` holds the conformance suite for the typed unit, `dfo_spec_kit.units`, which reads a unit ref into `money`, `unpriced_money`, `percent`, `count` or `other` by the rules in `registries/units.json`. Each vector is one JSON file named `<name>.json`, validated against `schemas/vectors/unit-vector.schema.json` by `tools/validate_unit_vectors.py`, and `python/spec-kit/tests/test_units.py` runs every file through the module.

A vector carries `format_version` (`1`), `name`, `description` and a `classification`, which decides the rest of the record:

- `parse`: `ref`, and `expected`, the typed value as a JSON object with every member present. Money is `{kind, currency, prices, base_year, chained}`, unpriced money `{kind, currency}`, per cent and a count `{kind}`, and other `{kind, ref}`.
- `compare`: `refs`, two refs; `measurement_qualifier`, a dcid or `null`, which completes both refs' unstated prices first; and `outcome`. `equal` and `different` say whether the two values compare equal. `incomparable` says the comparison raises because a value is unpriced money or is constant-price money with no `base_year`, since two unknown base years may differ.
- `complete`: `ref`, `measurement_qualifier` (a dcid or `null`), and `expected`, the typed value after `complete_prices` gives unpriced money the qualifier's price basis.

The suite uses real refs, typed and untyped. `Per1000Persons`, `Per100000Persons`, `IndexPoint`, `PPPInternationalDollar`, `SDG_CU_USD_M`, `CurrencyPerUSDollar` and `Currencyusd` are real refs that no registry row or prefix rule types, and the `other` vectors that use them prove they read as `other`. Adding a registry row for one of them changes those vectors. `TEU`, twenty-foot equivalent units, stands for a bare three-capital ref that is not a currency code. `test/unknownUnit` stands for a ref no import uses, and `test/unknownQualifier` for a qualifier that states no price basis.
